# Software Copyright Workflow

一个面向中国计算机软件著作权登记场景的 Codex Skill，用于把科研课题、算法、软件原型或已有项目，逐步整理为可验证的软件成果与相互一致的登记材料。

它关注的不只是“写一份文档”，而是建立以下内容之间的可追溯关系：

> 课题或需求 → 软件功能 → 实际实现 → 运行证据 → 用户手册 → 源代码鉴别材料 → 申请表

## 适用场景

本 Skill 适合以下工作：

- 只有科研课题、算法说明或项目设想，需要先定义可验收的软件。
- 已有原型或部分代码，需要补齐关键流程并确认真实功能。
- 已有可运行软件，需要整理用户手册、截图和源代码鉴别材料。
- 需要编写或校对软件著作权申请表中的功能、环境和版本信息。
- 需要检查申请表、用户手册、源代码和实际软件是否一致。
- 缺少同类项目、样例手册或参考源码，需要从现有事实出发独立完成材料整理。

它也可以用于局部任务，例如：

- 只修改“主要功能和技术特点”。
- 只审查用户手册。
- 只整理源代码鉴别材料。
- 只检查软件版本、截图和申请信息之间的一致性。

## 核心目标

工作完成后，应尽量形成以下成果：

1. 一个边界清楚、能够实际运行和验证的软件版本。
2. 一条从输入、参数、处理到输出的真实运行链路。
3. 软件功能与实现文件、操作入口、截图和材料表述之间的对应关系。
4. 与实际软件一致的用户手册。
5. 可追溯、经过必要清理的源代码鉴别材料。
6. 基于已确认事实编写的申请表内容。
7. 一份仍待核实事项清单，避免把推测写成事实。

## 工作流程

### 1. 判断项目起点

首先判断当前材料属于哪种情况：

| 起点 | 主要工作 |
| --- | --- |
| 只有课题或算法 | 定义软件用户、输入、核心处理、输出和首版功能 |
| 已有原型或部分代码 | 阅读实际入口和主要模块，补齐可运行链路 |
| 已有稳定软件 | 固定申报版本，采集证据并编写材料 |
| 只需修改或审查材料 | 严格限制在用户指定范围内工作 |

### 2. 将课题转化为可验收的软件

用一句话明确软件的基本闭环：

> 用户输入什么 → 软件执行什么处理 → 最终输出什么

随后整理：

- 目标用户和使用场景。
- 输入数据及其格式。
- 可配置参数、单位、来源和作用。
- 核心算法或业务流程。
- 输出结果、图表或文件。
- 首版功能清单。
- 每项功能可观察的验收结果。

对于缺少依据的参数，应标为“暂定”或设计为可配置项，而不是伪造来源。

### 3. 验证功能并锁定版本

优先验证一条真实链路：

1. 从实际入口导入或填写数据。
2. 设置参数并确认参数已正确传递。
3. 执行核心处理。
4. 检查运行状态、日志和异常。
5. 查看结果、图表或导出文件。
6. 保存软件版本、输入口径、参数和输出结果。

如果软件涉及优化计算，应区分：

- 无可行解。
- 已获得可行解。
- 达到约定精度。
- 已证明最优。

采用时间上限、近似算法或缩小样本时，需要如实说明范围和精度。

### 4. 建立实现与材料的对应关系

建议建立如下对应表：

| 功能 | 操作入口 | 实现文件或模块 | 运行证据 | 材料中的表述 |
| --- | --- | --- | --- | --- |
| 示例：导入数据 | 首页“导入”按钮 | 数据读取模块 | 导入成功截图或日志 | 支持指定格式的数据导入 |

无法验证的能力应标为待核实，并在核实前从正式功能描述中排除。

### 5. 编写用户手册

没有指定模板时，可采用以下结构：

1. 软件概述。
2. 系统要求与运行环境。
3. 安装或启动方式。
4. 功能概述。
5. 输入数据与参数设置。
6. 执行过程与状态查看。
7. 结果解读。
8. 图表查看与结果导出。
9. 常见问题或注意事项。

每个操作步骤应回答三个问题：

- 用户在哪里操作？
- 用户需要点击或填写什么？
- 操作完成后会看到什么？

截图应来自同一申报版本，优先使用同一次运行结果，并在正文中就近引用。

### 6. 整理源代码鉴别材料

整理时重点检查：

- 启动入口。
- 核心业务或算法模块。
- 数据处理代码。
- 实际界面代码。
- 文件边界和截取顺序。
- 申报功能与源代码是否一致。
- 当前申报渠道对页数、行数、格式和顺序的要求。

应在项目副本上整理材料，并清理：

- 本机绝对路径。
- 密钥、令牌和账号信息。
- 个人信息。
- 缓存和临时文件。
- 历史日志。
- 不需要提交的第三方依赖副本。

不要删除影响运行、编码或授权判断的重要声明。第三方代码、素材和数据还需要核实许可和署名义务。

### 7. 填写并核对申请材料

申请表内容应以已确认事实为基础。主要功能通常可按以下顺序组织：

> 使用对象与目的 → 输入和设置 → 核心处理 → 结果与交付

最终需要横向检查：

- 软件全称和简称。
- 版本号。
- 完成日期和发表状态。
- 运行环境。
- 功能范围。
- 操作入口。
- 参数、单位和结果口径。
- 申请主体、开发方式和权属信息。
- 用户手册、源代码和实际软件是否一致。

具体字段限制、上传格式和鉴别材料要求可能变化，应以实际申报渠道和当次官方指引为准，并记录核对日期。

## 安装

### 方式一：直接克隆到 Codex Skills 目录

```bash
git clone https://github.com/liu-sijia/software-copyright-workflow.git ~/.codex/skills/software-copyright-workflow
```

Windows PowerShell 示例：

```powershell
git clone https://github.com/liu-sijia/software-copyright-workflow.git "$HOME\.codex\skills\software-copyright-workflow"
```

安装后重新开始一个 Codex 会话，使 Skill 可以被发现。

### 方式二：手动安装

1. 下载或克隆本仓库。
2. 确保目录名为 `software-copyright-workflow`。
3. 将整个目录放入 Codex 的 Skills 目录。
4. 确认最终路径中包含 `SKILL.md`。

示例结构：

```text
~/.codex/skills/
└── software-copyright-workflow/
    ├── SKILL.md
    └── README.md
```

## 使用方式

可以直接描述任务，或明确指定本 Skill。

### 从课题开始

```text
请使用 software-copyright-workflow，把这份科研课题整理成一个可验收的软件方案，
先定义输入、核心处理、输出、首版功能和验收标准。
```

### 从已有代码开始

```text
请检查这个项目的实际入口和主要模块，建立“功能—实现—运行证据—申报材料”的对应表，
不要写入代码中无法验证的功能。
```

### 编写用户手册

```text
请根据当前可运行版本编写软件著作权用户手册。
操作步骤、截图说明、版本和运行环境必须与实际软件一致。
```

### 整理源代码鉴别材料

```text
请从项目副本整理源代码鉴别材料，保留文件边界，
检查并清理密钥、个人信息、本机绝对路径、缓存和历史日志。
```

### 审核整套材料

```text
请横向核对申请表、用户手册、源代码和实际软件，
列出名称、版本、环境、功能、入口和结果口径不一致的地方。
```

## 建议提供的输入

输入越完整，结果越容易核验。可以提供：

- 课题书、需求说明或算法说明。
- 项目源码或仓库。
- 软件启动方式。
- 示例输入数据。
- 参数说明及其来源。
- 运行日志和输出文件。
- 界面截图。
- 已有用户手册或申请表草稿。
- 软件名称、版本、完成日期和权属信息。
- 当前申报渠道或官方要求。

如果材料不完整，Skill 会优先使用能够确认的事实，并把关键缺口列为待核实事项。

## 典型交付物

根据任务范围，可能产出：

- 软件定义和首版功能清单。
- 功能验收标准。
- 参数及依据清单。
- 运行验证记录。
- 功能与实现对应表。
- 用户手册。
- 源代码鉴别材料。
- 申请表文字草稿。
- 材料一致性检查报告。
- 待核实事项清单。

实际提交申请、上传文件或代表申请人确认权属信息，需要用户明确授权。

## 重要原则

- **以实际软件为准**：不把规划中的能力写成已经实现的功能。
- **以证据为准**：功能描述应能够由代码、操作入口、日志、截图或输出验证。
- **版本一致**：软件、源码、截图、手册和申请表应对应同一版本。
- **参数可追溯**：记录参数的数值、单位、来源、作用和适用条件。
- **如实描述限制**：近似计算、样本缩小、时间上限和能力边界需要明确说明。
- **保护敏感信息**：整理源码前检查密钥、个人信息、路径、日志和缓存。
- **核实现行要求**：申报规则可能更新，应核对实际渠道的最新要求。
- **保留人工确认**：申请主体、权属、完成日期和发表状态等信息不能凭空推断。

## 能力边界

本 Skill 提供工作流程、核验方法和材料整理指导，但不能替代：

- 登记机构的现行官方要求。
- 对著作权归属和争议的专业法律意见。
- 申请人对主体、权属和开发事实的确认。
- 对未提供、无法运行或无法查看内容的真实性验证。
- 用户对最终材料和正式提交行为的审核与授权。
